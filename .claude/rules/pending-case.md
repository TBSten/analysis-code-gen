# 保留テスト（@PendingCase）の一方向ルール（R-01）

P1 で全テストケースを「未実装の保留」としてテストコードにしておき、P2・P3 で実装できたものから保留を外す。進捗は「保留を外して通ったケース数 / 全ケース数」で測る。

## 許される変化は 保留 → 有効 だけ

- 保留を外すのは、そのケースの実装が入り、テストが**期待値を変えずに**通ったとき（skill `enable-pending-case`）
- 一度有効にしたテストについて、次のことは**禁止**:
  - 保留に戻す（`@PendingCase` を付け直す、`disabled`・`xtest`・`!` 接頭辞・`enabled = false` などで止める）
  - 削除する、アサーションを減らす・緩める、期待値をいまの出力に合わせて書き換える
  - タイムアウトやリトライを増やして不安定さを隠す
- どうしても必要なときは、ADR に理由を書き、てべすてんに報告してからにする（チケットを「人間:判断待ち」に）
- 保留の理由は「未実装」と「ADR 付き」の 2 種類だけ。それ以外の理由で止めない

## ケース ID

- すべてのテストはケース ID（例: `GRD-01`）に結び付ける。ID は `quality/test-cases.csv`（ACG-37 で移すまでは共有フォルダ `quality/`）が正
- 保留にはケース ID と担当マイルストーン（M1 / M2 / M3）を付ける
- 実装中に気づいた新しいケースは一覧に直接足さず、`quality/case-backlog.md` に `CB-n` で溜める（分母を動かさない）。ただし「通っているケースの不具合」は既存 ID の回帰テストとしてすぐ足してよい
- ケースの削除・マイルストーンの後ろ倒しは ADR + 報告

## 不安定なテスト

- flaky は「通っていない」と数える。原因を直すまで有効のまま赤にしておき、チケットで追う
